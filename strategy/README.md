# Strategy 方案

## 方案概述

本方案通过策略选择 Dashboard 分组输出。`ClusterGrouper` 是输出策略接口，
`ServiceGroupStrategy` 和 `FlatTypeGroupStrategy` 分别选择嵌套分组或平铺结构；
`RenderDashboard` 将输入服务器委托给选定策略。`DefaultDashboardService` 和
`DefaultDashboardFlatService` 各自完成对应视图的聚合与排序，`Sorter` 则通过依赖
注入提供可替换的排序行为。没有服务的服务器进入独立的 `NoServiceType` 分组；平铺视图则通过 JSON 字段 `no_service` 返回，避免遗漏服务器。

该方案体现策略模式：调用方可在运行时选择输出策略。代价是策略接口以 `any` 返回
结果，调用方需要知道具体策略对应的结果类型；不同输出服务各自维护聚合流程，业务
规则变更时需注意保持两条流程一致。适合强调运行时可替换输出策略的场景；若视图集合
固定且需要强类型 API，可比较 builder 方案。

## 架构与设计模式

本包采用策略接口与依赖注入组合的结构。`ClusterGrouper` 定义可替换的输出策略，
`RenderDashboard` 负责把请求委托给所选策略；`Sorter` 则将排序行为独立出来，可由
调用方替换。`ServiceGroupStrategy` 与 `FlatTypeGroupStrategy` 分别构造对应的
Dashboard 服务，并各自完成聚合和排序。

该设计在运行时选择行为时较灵活，但策略入口返回 `any`，类型约束需由调用方维护；
同时两种视图各有一份聚合流程，新增或修改分组规则时要防止实现逐渐分叉。

## 可维护性与演进性分析

- **新增输出视图：**通常需要新增结果结构、Dashboard 服务和 `ClusterGrouper` 策略，
  并由调用方选择；扩展入口较直观，但新策略可能复制已有聚合代码。
- **调整分组或分类规则：**嵌套版和平铺版分别聚合，相关逻辑需要在两处核对和修改；
  这增加了行为漂移风险，不利于单一职责和避免重复。
- **新增排序算法：**可通过 `Sorter` 注入新的实现，但 `Sorter` 接口当前同时包含多种
  切片排序方法；改变接口会影响全部实现方，新增默认排序规则则需维护对应方法。
- **新增服务类型：**需更新优先级配置、类型常量、平铺结构及相应分派逻辑和测试；
  类型扩展并非只改一处。
- **新增分组规则：**没有独立的规则枚举和规则表；通常需新增策略或修改现有策略，
  并更新策略选择处及测试。只有选择策略的调用方不依赖具体实现时，才体现较好的
  开闭扩展性；`any` 返回限制了这种扩展的类型安全。
- **修改共同执行流程：**嵌套和平铺服务各自实现聚合，修改时需要分别维护；排序器
  提供一定职责隔离，但没有共享完整的分组骨架。
- **调整外部规则参数或序列化：**本包没有规则参数解析层；调用方负责策略选择。
  响应字段和 JSON 标签分布在结果结构中，变更时需校验相应输出契约。

总体而言，该方案在运行时替换策略方面灵活，但跨视图维护成本较高；适用于策略确实
需要独立实现、且运行时选择比聚合逻辑复用更重要的场景。
